# 医械法规云 · MedReg Hub

医疗器械法规全生命周期检索与溯源平台。覆盖中国 NMPA 全层级法规（含 GB/YY 标准）与海外重点市场准入要求，支持**全文检索、类目导航、条款级溯源、结构化下载、法规审查提示词组装、注册流程导航、文档审查与整改闭环、申报前自检、法规全文层、B2B 法规服务集市**。

**在线体验**：<https://medreg-hub.app.workbuddy.host/> ｜ **开源协议**：MIT ｜ **零依赖**：无 CDN、无框架、无后端

- 数据版本：v1.5.0 ｜ 最近核验：2026-09-17
- 法规库：**118 部法规 / 385 条核心条款要点 / 10 个市场与国际组织**（中国 82 部、海外 36 部）
- 注册流程：**10 条申报路径 / 57 个流程环节 / 121 号公告六大资料模块 27 项 / 3 组时限规则**
- 文档审查：**9 类文档 / 22 条要素覆盖规则 / 11 项规范检查 / 7 项术语一致性 / 3 组时限口径**，文档不上传、全程本地运行
- 申报自检：**75 条自检条目 / 3 级风险（红线·关键·建议） / 5 个阶段 / 适配 10 条申报路径**，红线未清即判定为「未就绪」
- 法规全文层：**7 条官方获取通道 / 逐条解析引擎 / 条文号回链核心要点**，平台**不内嵌、不转载**法规原文，导入文本仅存本机浏览器
- 法规服务集市：**8 家服务方 / 28 个服务包 / 覆盖 118 部法规中的 62 部**，双向贯通「法规↔服务」，**演示数据、不经手交易**
- 技术形态：纯静态前端，**零外部依赖**（无 CDN、无框架、无后端），双击即可离线运行

## 三、核心功能

**检索与导航**
- 标题 / 文号 / 发布机关 / 主题标签 / 条款正文五路加权检索，整词未命中时自动降级为中文二元组覆盖率匹配（解决「不良事件报告时限」这类无逐字命中的长查询）
- 类目条按市场快速切换；左侧筛选支持地区、效力层级、效力状态、发布机关、主题标签五维多选联动，实时显示各维度计数（标签维度自动限流显示前 24 项，已选项常驻）
- 五种排序：综合 / 最新发布 / 施行日期 / 引用热度 / 标题
- 六个业务场景入口：注册申报、生产与质量体系、上市后管理、软件与 AI 器械、海外准入、经营与供应链

**详情与溯源**
- 抽屉式详情页：法规定位、基础信息表（含来源机构与最近核验日期）、核心条款要点（折叠展开）、关联法规跳转、主题标签、标准引用格式
- 每一条目均带 `officialUrl` 官方入口，一键回溯发布机关公布页面
- **全文层区段**（v1.5.0）：按地区匹配官方全文通道，或导入自备文本逐条解析，条文号自动回链平台核心要点
- **服务方区段**（v1.5.0）：展示可承接本法规的市场服务方，直接进入集市
- 自动生成可复制的标准引用格式（含文号、层级、发布/施行日期、效力状态、来源、核验日期）

**下载与导出**
- 单条法规：Markdown / TXT / JSON
- 批量清单：CSV 台账（带 BOM，Excel 直接打开，18 列元数据）
- 结构化数据包：JSON（含导出时间、筛选条件、完整条目）
- **合规差距分析表**：按当前筛选结果自动生成条款级核对清单表格（含「符合性判定 / 责任部门 / 证据文件编号 / 整改完成日」空白列），可直接作为整改闭环的起始文档
- 下载中心：按市场打包下载（CSV 台账 / JSON 数据包 / 差距分析表 / 审查提示词）
- 我的法规库：收藏夹基于 `localStorage` 本地持久化

**法规审查提示词组装（v1.1.0 新增）**

把选定法规的条款要点自动组装为一份**结构化大模型审查提示词**，解决「有法规库、但不知道怎么喂给 AI 做审查」的断点。生成内容包含七个部分：

1. **角色设定** —— RA/QA 合规专家，判断必须基于给定法规依据
2. **审查任务** —— 明确审查重点、适用法规范围与海外差异提示
3. **法规依据清单** —— 每部法规附文号、层级、效力状态、施行日期、官方溯源链接与全部条款要点
4. **审查维度** —— 完整性合法性、内容准确性、文件间一致性、可追溯性、风险控制闭环、上市后义务
5. **输出格式** —— 总体结论 + 问题清单表格（判定 / 问题描述 / 整改建议 / 风险等级）+ 整改优先级 + 法规溯源清单
6. **硬性要求** —— 每条判定必须注明文号与条款编号，禁止虚构法规，不确定须标注「需人工确认」
7. **待审查文档** —— 预留粘贴位

入口有三处：列表工具栏的「🤖 生成审查提示词」（作用于当前筛选结果）、下载中心模板、法规详情页（自动带上该法规及其关联法规）。生成结果为 Markdown 文件，可直接粘贴到任意大模型使用。

## 三之二、注册流程导航（v1.2.0 新增）

顶栏「🏁 注册流程」进入。这一模块解决的是「**知道有哪些法规，但不知道怎么走完注册这条路**」的断点 —— 把法规库从「查得到」推进到「用得上」。全部内容以中国 NMPA 为口径，每个环节都挂载法规依据，可一键跳回法规库查看条款要点与官方溯源入口。

### 1. 属性界定与分类判定

四步判定路径（属性界定 → 查阅分类目录 → 目录外产品界定 → 形成判定记录），配 **8 项判定要素核对表**（结构特征、接触人体、接触时间、能量供给、生命支持、吸收代谢、特殊人群、失效后果），每项给出依《医疗器械分类规则》的核对问题、关注点与留白结论列；下方三张类别结论卡（一类 / 二类 / 三类）直接标注对应申报动作与办理机关，点击即跳转到该路径。

### 2. 十类申报路径

| 分组 | 路径 | 要点 |
| --- | --- | --- |
| 常规路径 | 第一类产品备案 | 设区的市级药监部门，资料齐全当场备案，备案编号长期有效 |
| 常规路径 | 第二类医疗器械注册 | 省级药监部门；技术审评 **60 个工作日** |
| 常规路径 | 第三类医疗器械注册 | 国家药监局 / CMDE；技术审评 **90 个工作日**，体系核查 10+30 个工作日 |
| 前置许可 | 第三类临床试验审批 | 受理起 60 个工作日内决定，**逾期未通知视为同意** |
| 加速通道 | 创新医疗器械特别审查 | 省级初审 20 个工作日；核心发明专利授权公告日起 5 年内申请 |
| 加速通道 | 医疗器械优先审批 | 临床急需 / 国家科技重大专项 / 优先审批目录 |
| 加速通道 | 医疗器械应急注册 | 突发公卫事件所需，检验、核查、审评**并行**推进 |
| 加速通道 | 附条件批准 | 先批准后补证据，注册证载明上市后研究义务与完成时限 |
| 证后维护 | 变更注册与变更备案 | 实质性变化走变更注册；其他变化 30 日内备案 |
| 证后维护 | 延续注册 | 有效期 5 年，**届满 6 个月前**申请，逾期视为放弃 |

每条路径展开后为**竖向时间轴**，逐环节给出责任方、时限徽标、环节说明与法规依据 chip；展开详情另有三类操作：导出本路径规划书、生成本路径法规审查提示词、查看本路径相关法规（回到法规库做精确范围过滤）。

### 3. 注册申报资料清单

按 2021 年第 121 号公告组织**六大模块 27 项**（监管信息 / 综述资料 / 非临床资料 / 临床评价资料 / 说明书和标签样稿 / 质量管理体系文件），支持逐项勾选并显示完成进度，导出时保留勾选状态（`- [x]` / `- [ ]`），可直接作为资料准备的工作底稿。

### 4. 时限推算

选择申报路径 + 输入受理日期，按官方规定的工作日上限逐环节累加，输出每个环节的**起算日与最晚完成日**、法定工作日合计、预计完成日与约合自然日。推算按工作日跳过周末；页面明确标注**未扣除法定节假日**，也未计入补充资料、核查后整改与质量管理体系核查所占用的时间。

### 5. 四类可交付文档

| 导出件 | 内容 | 用途 |
| --- | --- | --- |
| 《分类判定记录表》 | 判定路径 + 8 项要素核对表（留空列）+ 类别结论表 | 立项判定留痕、体系核查证据 |
| 《注册申报资料清单》 | 六大模块 27 项，带勾选状态 + 编制要点 | 资料准备分工底稿 |
| 《注册路径规划书》（单条） | 该路径全部环节、责任方、时限、法规依据、相关法规清单（含官方链接） | 路径立项与排期 |
| 《医疗器械注册路径规划书》（全量） | 决策总览 + 分类判定 + 10 条路径环节表 + 资料清单 + 时限口径 + 相关法规清单 | 项目整体注册策略 |

时限数据口径为《医疗器械注册与备案管理办法》（市场监管总局令第 47 号）第七章，其中**第九十九条明确「本办法规定的时限以工作日计算」** —— 本模块的推算即按此口径。

## 三之三、文档审查工作台（v1.3.0 新增）

顶栏「🔍 文档审查」进入。这一模块解决的是「**文档写完了，但不知道能不能过、哪里会被要求补正**」的断点 —— 把法规库从「用得上」推进到「审得住」。文档**不上传、不联网**，审查在浏览器内完成，便携版同样可用。

### 1. 审查基准（本次拿哪些法规当尺子）

| 基准 | 说明 |
| --- | --- |
| 🏁 按注册路径 | 取该路径全部环节挂载的法规，例如「第三类医疗器械注册」自动带入 14 部 |
| 🎯 按业务场景 | 复用首页六大场景（注册申报 / 生产质量 / 上市后 / 软件 AI / 海外准入 / 经营供应链） |
| ✋ 自定义范围 | 关键词逐部加入，或一键导入「我的法规库」「当前筛选结果」 |
| 📚 全库法规 | 118 部全量纳入 |

已纳入的法规以 chip 展示，点开即看条款要点与官方溯源入口。

### 2. 文档提交

九类文档类型（注册申报资料包 / 产品技术要求 / 风险管理报告 / 研究资料 / 软件研究资料 / 临床评价报告 / 说明书与标签 / 质量管理体系文件 / 上市后管理文件）决定应有的**章节结构**与**适用的检查规则**。

提交方式：直接粘贴文本，或上传 .txt / .md / .csv / .json / .docx。**`.docx` 解析为零依赖实现** —— 用浏览器原生 `DecompressionStream` 解开 OOXML 压缩包、抽取 `word/document.xml` 文本，不引入任何第三方库。另内置两份含**刻意设置缺陷**的示例文档，用于演示与回归（校验脚本会用规则正则对示例文本实跑一遍，确认规则真的会命中）。

### 3. 审查引擎（确定性规则，非模型猜测）

| 维度 | 规则量 | 检查方式 |
| --- | --- | --- |
| 结构完整性 | 9 类文档各 4~6 章节 | 按文档类型应有章节逐项比对关键词 |
| 要素覆盖 | 22 条 | AND-of-OR 词组：每组必须命中一个同义词，未命中即判缺失 |
| 表述规范性 | 11 项 | 正则：占位符、绝对化用语、失效版本、标准未标年号、缺计量单位、半角标点、未标文号的引用… |
| 术语一致性 | 7 项 | 同一概念多称谓混用 / 非规范写法（「禁忌症」「不良事故」等） |
| 时限口径 | 3 组 | 抓取文档中的时限数值与法规口径比对（召回 1/3/7 日、不良事件 7/20 日、延续注册 6 个月） |

两个关键取舍：

- **`when` 触发词**：生物学评价、电气安全、软件、灭菌、委托生产等规则只在文档出现相关线索时才评估，避免整篇「与己无关」的缺失误报。
- **命中归属去重**：时限核对按匹配区间去重，避免「严重伤害、可能导致严重伤害或者死亡」这类并列表述把 20 日的时限错记到「死亡」名下；同时对「境外发生」的 30 日报告口径单独排除，不按境内时限误判。

### 4. 审查报告与四类导出

报告含：合规成熟度评分（100 分制，高 -6 / 中 -3 / 低 -1，用于横向比较与改进跟踪）、要素覆盖率、问题维度分布、按风险等级排序的问题清单（每条附命中**行号与原句**、法规依据 chip、整改建议与依据条款），以及「已满足的要求」清单（可作为符合性证据线索）。

| 导出件 | 用途 |
| --- | --- |
| 《文档审查报告》（Markdown） | 审查概况 + 法规依据清单 + 问题清单表 + 命中明细 + 结论建议，可直接进项目文档 |
| 《问题清单》（CSV） | 含「责任部门 / 计划完成日 / 整改状态」空白列，直接作为整改台账 |
| 《整改计划表》（Markdown） | 按「立即整改 / 限期整改 / 持续改进」三档分组，含建议责任部门与验证方式 |
| 《深度审查提示词》（Markdown） | 把**文档全文 + 法规依据 + 本地疑点清单**组装为结构化提示词，交大模型逐项确认或排除 |

工作台与注册流程模块已打通：每条路径的展开详情里有「🔍 带本路径法规去审查文档」，一键把该路径的法规设为审查基准。

## 三之四、申报前自检清单（v1.4.0 新增）

文档审查工作台回答的是「文档写完之后，哪里写错了」；申报前自检清单回答的是「申报之前，我是不是都准备好了」。前者是事后诊断，后者是事前防漏，两者共用同一套法规依据。

### 1. 路径驱动，而不是一张通用清单

自检清单不提供一刀切的检查表。选定申报路径后，引擎按三条规则自动组装该路径适用的条目：

- 条目声明 `paths`（白名单）时，只在该路径下出现；
- 声明 `not`（黑名单）时，除列出的路径外均适用；
- 路径档案 `mode` 为 `delta`（变更注册、延续注册）时，只收录显式声明该路径的条目 —— 增量申报不适用全套首次注册自检。

组装结果：第一类备案 **53 项**（自动豁免临床评价与注册体系核查相关条目）、第二类注册 **57 项**、第三类注册 **58 项**、创新/优先/应急/附条件 **58~59 项**、变更注册与延续注册各 **6 项**专属条目。

### 2. 三级风险分级

| 等级 | 条目数 | 含义 | 权重 |
| --- | --- | --- | --- |
| ⛔ 红线项 | 30 | 不满足将直接导致不予受理、不予注册或体系核查不通过 | 30 |
| ⚠️ 关键项 | 34 | 直接影响审评结论，缺失会引发发补、显著延长审评周期 | 10 |
| 💡 建议项 | 11 | 不构成硬性缺陷，但完善后可降低沟通成本、提高一次性通过概率 | 3 |

### 3. 五阶段覆盖申报全流程

**一 · 立项与路径决策** → **二 · 研究与验证** → **三 · 资料编制** → **四 · 申报与受理** → **五 · 审评应对与上市后准备**。

每条自检项含六个字段：**自检提问**（可直接勾选的是非问句）、**判定要点**、**应备证据**清单、**常见退回 / 发补原因**、**法规依据**（可点开法规详情抽屉）、**相关文档类型**（一键跳转到文档审查工作台并预设文档类型）。

### 4. 三态标记与申报就绪度

每条目可标记为「✓ 已满足 / — 不适用 / ↺ 重置」三态。就绪度按风险权重加权计算：

> 就绪度 = Σ（已处理条目权重）÷ Σ（全部条目权重）× 100%

**红线项未清空前，结论固定为「未就绪」并给出醒目预警** —— 这是刻意的硬约束，避免用「总体完成度很高」掩盖致命缺口。标记自动保存在本机浏览器（localStorage，按申报路径分别存储），不上传、不联网。

### 5. 四类导出

| 导出件 | 用途 |
| --- | --- |
| 自检报告（Markdown） | 就绪度评分、分阶段自检结果表、红线 / 关键待确认清单、法规依据索引 |
| 缺项清单（CSV） | 仅导出尚未确认的条目，含判定要点、法规依据与责任部门 / 计划完成日 / 整改状态等空白列，直接作为整改台账 |
| 空白自检表（Markdown） | 三态勾选表，可打印下发给跨部门自检小组逐项签认 |
| 自检结果（JSON） | 结构化导出，供内部系统或 Agent 二次使用 |

### 6. 与其他模块的联动

- **注册流程页 → 自检清单**：「生成该路径的自检清单」一键带入路径；
- **自检清单 → 注册流程页**：侧栏可回看本路径的完整流程环节与时限推算；
- **自检项 → 文档审查**：点击条目中的「相关文档类型」跳转到审查工作台并预设文档类型；
- **下载中心**：三个模块入口并列，模板卡可直接生成自检报告与缺项清单。

## 三之五、法规全文层（v1.5.0 新增）

前四个模块都在回答「**要点够不够用**」，这一层回答的是「**要点之外，原文从哪来**」。法规详情页在「核心条款要点」下方新增全文区段，采用**双层结构**：

| 层 | 提供什么 | 边界 |
| --- | --- | --- |
| 要点层（原有） | 人工整理的结构化条款要点、法规定位、关联法规、引用格式 | 非官方逐字全文，已在 UI 与导出件中明确标注 |
| 全文层（本版） | 官方逐字全文的**获取通道** + 用户自备文本的**本地逐条解析** | 平台**不内嵌、不转载、不分发**任何法规原文 |

### 1. 官方获取通道（按地区自动匹配）

内置 **7 条官方通道**，按法条所属地区自动匹配，每条给出发布机关、文件格式与使用提示：

| 通道 | 覆盖范围 | 权威来源 |
| --- | --- | --- |
| `ch-gov` | 中国 · 行政法规 / 规范性文件 | 中国政府网 |
| `ch-nmpa` | 中国 · 部门规章 / 公告通告 | 国家药品监督管理局 |
| `ch-cmde` | 中国 · 技术审评指导原则 | 国家药监局器审中心 |
| `ch-sac` | 中国 · GB / GB-T 国家标准 | 国家标准全文公开系统 |
| `ch-nifdc` | 中国 · YY / YY-T 行业标准 | 中国食品药品检定研究院 |
| `ch-ecfr` | 美国 · 21 CFR 全文 | eCFR 电子法规汇编 |
| `ch-eurlex` | 欧盟 · MDR / IVDR 及配套条例 | EUR-Lex |

日本、韩国、加拿大、澳大利亚、巴西、印度（JP / KR / CA / AU / BR / IN）暂未配置默认通道 —— 此时全文区段自动**降级为 `officialUrl` 官方溯源入口**，而不是留一个空框，保证任何一条法规都有可追溯的下一步。

### 2. 本地导入 + 逐条解析

用户自行从官方渠道取得文本后，可在区段内粘贴或上传 `.txt / .md` 文件，引擎按正则切分为**章 / 条**结构：

- 条文识别：`第X条`（含中文数字、阿拉伯数字、全角空格分隔）
- 章节识别：`第X章`
- 单条正文限长 60 ~ 800,000 字符，避免把目录页或乱码文本错切成条文

解析结果以折叠列表呈现，每条显示**条号 + 正文**；正文中的条号会自动与平台既有的「核心条款要点」做**回链对照** —— 点开某一条，若平台要点层收录了该条号，会并排显示「平台要点」，实现「原文 ↔ 要点」双向印证。

### 3. 数据边界（刻意的设计约束）

| 约束 | 实现方式 |
| --- | --- |
| 不内嵌法规原文 | 数据卷 `data/fulltext.js` **不含任何条文容器**（`entries` / `articles` / `texts` / `fullText`），校验脚本明确禁止出现 |
| 演示素材必须显著标注 | 内置演示文本每一条正文都带「【演示文本·非真实法规条文】」前缀，校验脚本逐条断言 |
| 导入文本不出本机 | 仅写入 `localStorage`（键 `medreg.fulltext`），不上传、不联网，便携版同样可用 |
| 要点与原文可溯源 | 全文层导出件强制携带 `officialUrl` 溯源声明，避免导出的文本被误当作权威版本流转 |

### 4. 与审查模块的联动

- **文档审查 → 全文层**：每条审查问题新增「📖 查全文依据」，带着该问题的法规与**关键词**跳到全文层直接定位（`data-ft-jump` + `data-ft-q`）；
- **自检清单**：条目中的法规依据同样可一键跳全文层核验；
- **下载中心**：新增「全文导入册」导出 —— 把已导入的法规汇总为一份带溯源声明的 Markdown 册子，供离线专题研读。

## 三之六、B2B 法规服务集市（v1.5.0 新增）

顶栏「🏪 法规集市」进入。这是「**阿里模式**」在本平台的落地形态 —— 不做 C 端法规阅读器，而是把法规库变成**需求与服务方的撮合底座**：企业拿着自检缺项或审查问题，直接找到能承接的服务方。

> ⚠️ **平台边界**：集市当前为**演示数据**，服务方、报价、成交量为构造样例；平台**不经手交易、不做支付、不担保履约**。真实接入需替换为经审核的服务方名录并另行约定合同与资金路径。

### 1. 八个服务类目（对齐企业真实断点）

| 类目 | 定位 | 类目 | 定位 |
| --- | --- | --- | --- |
| `reg-test` | 注册检验 / 型式试验 | `qms-gmp` | 质量体系与 GMP 辅导 |
| `reg-agent` | 注册代理与申报代办 | `sw-ai` | 软件与 AI 器械专项 |
| `clin-eval` | 临床评价与试验 | `global-ma` | 海外准入与多国代理 |
| `data-tool` | 数据工具与信息化 | `post-market` | 上市后监测与再评价 |

**28 个在架服务包**分布为：检验 4 / 代理 4 / 临床 3 / 软件 AI 4 / 体系 5 / 海外 4 / 数据 2 / 上市后 2。

### 2. 八个服务方铺位

每家铺位含**等级（tier）、评分（0~5）、服务包数、响应时效（分钟）、履约率（0~100%）、资质标签（certs）与认证状态**。列表页支持按类目、服务方类型、地区、价格模式、关键词筛选，四种排序（综合 / 评分 / 快响 / 价格），以及「热榜 / 口碑 / 快响 / 新上」四个榜单。

### 3. 服务包与法规强绑定

每个服务包的 `covers` 字段是**法规 id 数组**，由校验脚本强制检查 —— 引用必须指向真实存在的法规，不允许「凭感觉写覆盖范围」。当前 **28 个服务包合计覆盖 118 部法规中的 62 部**，覆盖率可被量化跟踪。

这带来两个关键的双向入口：

- **法规 → 服务**：法规详情页底部展示「可承接本法规的服务方」（`mkRegServicesHTML`），把「我读到这条法规但不会做」直接接上服务；
- **服务 → 法规**：服务详情页列出覆盖的法规，点击回到法规库查看条款要点与官方溯源。

### 4. 询价单（不改交易、只做撮合前一步）

服务包可加入**询价车**，导出两种格式：

| 导出件 | 内容 |
| --- | --- |
| 询价单（CSV） | 服务包、服务方、价格模式、周期、交付物、覆盖法规，附「联系人 / 意向时间 / 预算区间 / 特殊要求」空白列 |
| 询价单（Markdown） | 分服务方归组的对话式询价正文，可直接发给服务方 |

询价车数据同为本机 `localStorage`（键 `medreg.market.cart`），不上传。集市页另有一处**边界声明**常驻展示（`demo === true` + 「不经手交易」文案），校验脚本强制校验其存在。

### 5. 与审查 / 自检的联动

- **文档审查 → 集市**：每条问题新增「🏪 找服务商解决」，按**文档类型优先、审查维度兜底**映射到服务类目 —— 产品技术要求 / 说明书标签 → `reg-agent`，风险管理报告 / 临床评价报告 → `clin-eval`，软件研究资料 → `sw-ai`，质量管理体系文件 → `qms-gmp`，上市后管理文件 → `post-market`；文档类型不适用时按维度兜底（结构 / 覆盖 / 规范性 → `reg-agent`，术语一致性 → `data-tool`，时限口径 → `post-market`，电气与网络安全 → `sw-ai`），同时保留原问题的法规上下文；
- **自检清单 → 集市**：每条自检项新增「🏪 找服务商承接该事项」，按该条目的法规依据过滤出覆盖服务方；
- **下载中心**：新增「🏪 打开法规服务集市」与询价单模板卡（`tpl-rfq`）。

### 扩充法规的标准流程

1. 新增条目一律写入 `data/regulations-cn-ext.js`（国内）或 `data/regulations-intl.js`（海外），务必包含全部 16 个必填字段。
2. 运行数据集校验：
   ```
   node tools/validate.js      # 输出 tools/validate-report.txt
   ```
   校验项：语法、必填字段、日期格式、id 去重、`related` 引用是否指向存在的 id。
3. 运行页面自测：
   ```
   NODE_PATH="<node-workspace>/node_modules" node tools/smoke.js   # 输出 272 项结果
   ```
4. 重新构建便携版：
   ```
   node tools/build-standalone.js && NODE_PATH="<node-workspace>/node_modules" node tools/smoke-standalone.js
   ```

### 注册流程数据（`data/registration-flow.js`）

注册流程模块的数据独立成卷，结构为 `window.MDR_FLOW`：

```js
{
  classify: { steps: [...], factors: [...], decision: [...] },  // 分类判定
  pathways: [ { id, group, icon, name, applicable, org,
                deadline, result, steps: [ { no, name, org, due, detail, basis: [] } ],
                notes: [], basis: [] } ],                       // 申报路径
  dossier: { basis, groups: [ { no, name, items: [] } ], tips: [] },  // 资料清单
  timelines: [ { id, name, org, phases: [ { name, workdays, basis } ], note } ],
  timelineRules: []                                             // 时限口径
}
```

其中 `basis` 字段统一存放**法规 id 数组**，由校验脚本强制检查其指向的法规必须存在于法规库中 —— 这样流程与法规库不会脱节，任何法规条目改名或删除都能被校验立刻发现。

### 审查规则数据（`data/review-rules.js`）

```js
{
  docTypes: [ { id, icon, name, desc } ],                    // 文档类型
  dimensions: [ { key, name, desc } ],                       // 审查维度
  docStructures: { tech: { name, basis, sections: [ { name, kw, optional } ] } },
  coverage: [ { id, dim, level, name, types, when, need: [[同义词…]], tip, fix, basis } ],
  patterns: [ { id, kind, dim, level, name, re, msg, fix, basis } ],
  terms:    [ { id, name, level, variants, wrong, prefer, msg, fix, basis } ],

  sampleDocs: [ { id, name, type, note, text } ]

```

`basis` 同样是**法规 id 数组**，校验脚本强制检查引用有效；此外校验还会用规则正则直接跑示例文档，确认**每条规则确实会命中**、且每类文档的适用规则不少于 5 条。引擎对外暴露 `window.MedRegReview.{rules, run, prompt, report}`，便于脚本化批量审查。

> ⚠️ **两个必须遵守的约束**
> 1. 数据文件为 JS 字符串字面量，**条款文本内不可出现 ASCII 双引号**（会截断字符串导致语法错误）。中文引号请使用 `「」`，书名号使用 `《》`。这是扩充数据时最容易踩的坑。
> 2. **不要在同一批次工具调用里对同一个文件发起多次编辑**，会因读写竞态互相覆盖。串行编辑，或写一次性脚本批量原子替换。

> 📌 文号与日期以官方来源核验为准（国家药监局公告通告、国家标准全文公开系统、中国政府网、eCFR / EUR-Lex）。**不确定发布日期的条目宁可不收录**，也不写推测值 —— 溯源准确度比条目数量更重要。

### 自检清单数据（`data/self-check.js`）

```js
window.MDR_SELFCHECK = {
  version, updatedAt, notice,
  levels:    [{ id, name, icon, weight, desc }],   // 三级风险与权重
  stages:    [{ id, no, icon, name, desc }],       // 五阶段
  pathRules: [{ id, mode, label, hint }],          // 路径档案，mode 为 full 或 delta
  items: [{
    id, stage, level, title, ask, detail, evidence[], pitfall, basis[],
    docs?[],    // 关联的文档审查类型，用于跨模块跳转
    paths?[],   // 白名单：仅这些申报路径适用
    not?[]      // 黑名单：除这些申报路径外均适用（与 paths 互斥）
  }]
};
```

校验脚本会强制核查：条目 `basis` 指向的法规必须存在、`stage` 与 `level` 必须已声明、`docs` 必须是合法文档类型、`paths` 与 `not` 必须指向真实申报路径且不得同时声明、`ask` 必须是自检问句；并要求每条申报路径都能组装出足量条目（full ≥ 20、delta ≥ 4）且至少包含一项红线项 —— 否则就绪度评分失去意义。

### 全文层数据（`data/fulltext.js`）

```js
window.MDR_FULLTEXT = {
  version, updatedAt,
  policy: { points: [...], notice },     // 不内嵌 / 不转载 / 仅本机的政策声明（≥3 条）
  channels: [{                            // 官方获取通道
    id, name, issuer, url,                // url 必须为 https
    format, scope, tip, applies          // applies：适用的地区代码数组
  }],
  byRegion: { CN: ["ch-gov", "ch-nmpa", ...] },   // 地区 → 通道 id；未配置的地区降级 officialUrl
  parse: { articlePattern, chapterPattern, minChars, maxChars },
  demo: "...",                            // 演示素材，每一条正文必须带【演示文本·非真实法规条文】
  coverageNote: "..."                     // 官方全文获取与本地导入的使用说明
};
```

校验脚本会编译 `parse` 的两条正则确认可用、用演示素材实跑一遍解析（断言能切出 ≥3 条且每条都带演示标记）、核查 `byRegion` 中的通道 id 均存在、`channels[].url` 均为 https；**并明确禁止**数据卷中出现 `entries` / `articles` / `texts` / `fullText` 等条文容器字段 —— 从数据层就堵住「把法规原文塞进平台」的可能。

### 集市数据（`data/market.js`）

```js
window.MDR_MARKET = {
  version, updatedAt,
  demo: true, notice: "...",             // 必须声明演示数据 + 不经手交易

  offerCats:   [{ id, icon, name, desc }],  // 服务类目（8 类）
  vendors: [{ id, name, type, tier, region, rating, reviews, deals,

              tags[], rating, reviews, deals, badges[] }],

  steps: [...],                           // 平台边界与撮合流程（≥3 步）

};
```

校验脚本会强制核查：`offers[].covers` 每一项都必须是**真实存在的法规 id**；`price.mode` 必须是 `quote / from / package` 之一，且 `from / package` 必须给出 `amount`；`vendors[].tier / verified / rating / fulfill` 类型与取值区间合法；每个服务类目与每家铺位至少各有 1 个在架服务包；覆盖的法规总数 ≥ 30；四个榜单均非空；`demo === true` 且 `notice` 同时提及「演示」与「不经手交易」。（当前：覆盖 62 / 118 部。）

**B2B 法规服务集市**：当前在架铺位、服务包、报价、评分与成交量均为**演示数据**，用于呈现产品形态，不代表任何真实服务方或其服务能力。平台**不经手交易、不提供支付通道、不担保履约**，不构成对任何服务方的推荐或背书。真实的供需对接、资质核查与合同签署须由双方另行完成。

AI 审查提示词所生成的分析结果仅为辅助参考，**不得作为合规结论、注册申报或法律意见的依据**，须经具备资质的合规人员复核。
